# Test Plan
# Test Plan

## 1. Purpose

This document defines the verification strategy for the Internal Incident & Work Tracker.

Testing must focus on business correctness, API behavior, state transitions, integration between clients and backend, and regression prevention.

---

# 2. Testing Principles

Tests should provide confidence in real behavior.

Prefer:

* focused tests
* deterministic tests
* meaningful assertions
* realistic domain data
* regression coverage for known bugs

Avoid tests that merely confirm implementation details without verifying behavior.

---

# 3. Backend Testing

## 3.1 Model Tests

Verify:

* Project creation
* Work Item creation
* Comment relationships
* Activity relationships
* timestamps
* required fields
* reference number format

---

# 4. Reference Number Tests

Verify:

* reference is generated by backend
* reference follows expected format
* reference is not supplied by the client
* references are unique
* sequential development references behave correctly

Consider higher-concurrency implications during technical review even though SQLite is sufficient for this challenge.

---

# 5. Workflow Tests

Test valid transitions.

At minimum:

```text
OPEN → IN_PROGRESS
IN_PROGRESS → REVIEW
REVIEW → RESOLVED
RESOLVED → CLOSED
```

Test invalid transitions.

At minimum:

```text
OPEN → CLOSED
```

must fail.

---

# 6. Resolution Tests

Verify that RESOLVED requires:

* assignee
* non-empty resolution note

Test:

1. no assignee + no note
2. assignee + no note
3. no assignee + note
4. assignee + note

Only case 4 should succeed.

---

# 7. Partial PATCH Tests

This is a mandatory high-value test area.

Test PATCH requests where fields are omitted.

Examples:

```json
{
  "status": "RESOLVED"
}
```

and:

```json
{
  "resolution_note": "Issue resolved."
}
```

Validation must correctly account for existing model values.

The implementation must not assume every field exists in a partial request.

---

# 16. Overdue Tests

Verify overdue behavior based on:

```text

AND

```

* overdue open item
* overdue in-progress item
* overdue review item
* resolved overdue-date item
* closed overdue-date item
* future due date

# 19. Kanban Testing

This is a critical area.

Test:

### Successful transition

```text
drag card
→ transition request
→ backend accepts
→ board reconciles
```

### Rejected transition

```text
drag card
→ transition request
→ backend rejects
→ error displayed
→ card restored to correct state
```

The UI must never remain in a state that contradicts the backend.

# 21. Regression Testing

After modifying shared functionality, rerun tests for affected systems.

Examples:

Changing workflow logic should trigger:

* workflow tests
* API tests
* Kanban verification
* detail-page transition verification
* Flutter transition verification

Changing API response structure should trigger:

* backend API tests
* web typecheck/build
* affected web UI tests
* Flutter analysis/build where applicable

# 23. Manual End-to-End Test

Perform the complete workflow:

```text
Create work item
    ↓
Assign developer
    ↓
Move to IN_PROGRESS
    ↓
Move to REVIEW
    ↓
Add resolution note
    ↓
Resolve
    ↓
Close
```

Verify activity history throughout the process.

Then deliberately attempt an invalid transition and verify rejection/recovery.

---

# 24. Test Completion Rule

Do not declare the system tested because automated tests pass.

Automated tests verify known behavior.

Manual verification must confirm that the complete application actually works as a user would experience it.

Both are required before final submission.
